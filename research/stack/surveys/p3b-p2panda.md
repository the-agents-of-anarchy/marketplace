## p2panda-net (commit c99f501, crate 0.7.1, iroh 1.3.0, iroh-gossip 0.101.0)

### Shape
- Crate 0.7.1, 12 releases on crates.io, newest 2026-08-21 (crates.io API).
- Default features: `address_book`, `iroh_endpoint`, `iroh_mdns`, `discovery`, `gossip`, `sync` (`p2panda-net/Cargo.toml`, `[features]`).
- Layers are separate builders over one endpoint: `Endpoint`, `AddressBook`, `Discovery`, `Gossip`, `MdnsDiscovery`, `LogSync` (`lib.rs`, module list and docs).
- Crates it adds on top of the estafette tree: `iroh`, `iroh-base`, `iroh-gossip`, `iroh-mdns-address-lookup`, `p2panda-core`, `p2panda-discovery`, `p2panda-store` (sqlite via `sqlx` 0.9.0), `p2panda-sync`, `ractor` 0.16.2, `postcard`, `rand_chacha`.

### Identity: one key for the peer and the transport
- A node's id is `NodeId = p2panda_core::VerifyingKey` (`lib.rs:287`).
- The iroh endpoint secret key is built from the same p2panda signing key bytes: `from_signing_key` (`utils.rs:126-128`), applied at `iroh_endpoint/actors/endpoint.rs:203`.
- `to_verifying_key` converts the iroh public key back (`utils.rs:116-118`). So `NodeId` and the iroh endpoint id are the same 32 bytes.
- The signing key is caller-supplied. If none is given, `SigningKey::default()` generates a fresh random key (`iroh_endpoint/builder.rs:98`, `p2panda-core/src/identity.rs:51-54`). A fresh endpoint therefore has a new node id unless the caller persists the key.
- There is no separate card, claim, or machine key layer. The transport key is the identity.
- Node and transport records are signed by that key. The address book verifies both on insert (`address_book/actor.rs:194` for node info, `:215` for transport info against the node id).

### Membership: network id is public, topic is the secret
- `NetworkId` is a 32-byte value that partitions protocols (`lib.rs:303`). It is hashed into each ALPN with BLAKE3 (`lib.rs:321-326`, `hash_protocol_id_with_network_id`).
- The crate says the network id "is _not_ confidentially exchanged" and "can not be treated as a secret value" (`lib.rs:301-302`, citing issue #965). `lib.rs:207-208` repeats this.
- The default network id is a public constant, `DEFAULT_NETWORK_ID` (`lib.rs:316-318`). It applies when the builder gets no id (`iroh_endpoint/builder.rs:97`).
- Mixed ALPNs: protocols are registered and connected under the mixed id (`iroh_endpoint/actors/endpoint.rs:232`, `:249`). Gossip uses the mixed `iroh_gossip::ALPN` (`gossip/actors/manager.rs:135`).
- Gating by topic: a `Topic` is 32 random bytes. The crate warns it must be treated as a secret and generated by a CSPRNG (`p2panda-core/src/topic.rs:25-29`). The application supplies it. `Topic::from([u8; 32])` and `from_bytes` accept any 32 bytes (`topic.rs:41`, `:64`).
- Discovery is the confidential part. The PSI protocol exchanges salted hashes of topics so two nodes learn only their shared topics (`p2panda-discovery/src/lib.rs` module docs, `psi_hash.rs:57-66`).
- Gossip uses the topic as its only join key. `Gossip::stream(topic)` joins the overlay and bootstraps from address-book entries that carry that topic (`gossip/api.rs:148`, `:178`). It does not use a ticket or a configured bootstrap list.
- Not found: an admission check in iroh-gossip. I did not find a check that a remote peer must hold the topic beyond presenting its id. I did not trace the wire framing end to end, so this stays a finding of absence.
- Authoriser: allow and block lists exist as an opt-in endpoint hook (`iroh_endpoint/authoriser.rs:24-27`). Default mode is `Permissive` (`:101`). Nothing is blocked unless configured.

### Discovery (PSI and random walk)
- Random walker picks a bootstrap from the address book, then walks with backoff (`discovery/actors/walker.rs:23` `NO_RESULTS_DELAY` 2 s; backoff defaults in `discovery/backoff.rs:47-58`: max wait 30 s between walks, reset every 60 s to 3 min).
- A session runs `PsiHashDiscoveryProtocol::new` with `Config::default()` (`discovery/actors/session.rs:122`, `p2panda-discovery/src/psi_hash.rs:78-84`).
- The default config sets `share_nodes_with_common_topics: false` (`psi_hash.rs:49-55`, derived `Default`). The sharing branch then uses `all_node_infos()` (`psi_hash.rs:140`), not only nodes with a common topic.
- Consequence: a discovery peer receives transport info for every node in the address book, including nodes that share none of your topics. The doc on `gather_transport_infos` (`psi_hash.rs:104-106`) says "We don't share any node infos outside of this scope for privacy reasons." The config doc (`psi_hash.rs:52-53`) says the protocol "will only share transport infos of nodes which have at least one common topic". The default contradicts both.
- The discovery QUIC config has a shorter idle timeout to mark unreachable nodes stale quickly (`discovery/actors/manager.rs:262-275`).

## Gossip, presence, departure (p2panda-net and its iroh-gossip dependency)

### Gossip payloads carry no sender
- Publish takes raw bytes: `publish(bytes)` (`gossip/api.rs:312`). p2panda adds no envelope and no signature.
- Subscribers receive `Vec<u8>` only (`gossip/api.rs:354-357`, `BroadcastStream<Vec<u8>>`). The manager's receive arm binds `bytes, topic` and drops the rest with `..` (`gossip/actors/manager.rs:300`).
- Underneath, iroh-gossip 0.101.0 delivers `Message { content, scope, delivered_from }`. The field doc says `delivered_from` "is not the same as the original author" (iroh-gossip `src/api.rs:363-371`). A grep of its non-test source found no signing or verification.
- Result: an application on p2panda-net cannot learn who originated a gossip payload. It learns at most the neighbour that delivered it, and p2panda discards even that.

### Events
- Four gossip events: `Joined { topic, nodes }`, `NeighbourUp`, `NeighbourDown`, `Left` (`gossip/events.rs:10-25`).
- `Joined` carries the initial neighbour set from the join (`gossip/actors/manager.rs:305-323`). `NeighbourUp` and `NeighbourDown` come from iroh-gossip's neighbour events (`gossip/actors/session.rs:196-212`, `gossip/actors/manager.rs:325-362`).
- `Left` fires when a topic loses its last handle (`gossip/actors/manager.rs:287`).
- No event or message type for a member announcing arrival or departure. The only departure-shaped signal is `NeighbourDown`, which is an overlay-level fact about direct neighbours.

### Presence: how a node learns the network
- Joining: `Gossip::stream(topic)` bootstraps from address-book nodes that carry the topic (`gossip/api.rs:178`). An empty result passes no bootstrap peers to the overlay join (`gossip/api.rs:178-200`).
- Re-joining: the healer subscribes to the address book's topic set and rejoins when that set changes (`gossip/actors/healer.rs:105-109`). It also rejoins when its own transport info changes (`:126`).
- Source of new nodes: discovery's PSI sessions (see the discovery section). New transport info reaches the address book, and the topic set changes, which triggers the healer.
- Introduction on join: none. A new node does not broadcast its claim. Known nodes are learned by the walker and by the gossip join.
- Periodic traffic: the walker runs continuously, at most 30 s between walks by default (`discovery/backoff.rs:47-58`, `discovery/actors/walker.rs:23`).

### Departure and liveness
- Clean stop: dropping the last `Gossip` handle sends `Shutdown` to the manager (`gossip/api.rs:232-245`, `gossip/actors/manager.rs:366`). iroh-gossip's shutdown "sends `Disconnect` messages to peers" (iroh-gossip `src/net.rs:254-257`). Direct overlay neighbours see `NeighbourDown`. I found no propagation of the disconnect beyond direct neighbours.
- No p2panda-level departure message exists. Grep for depart, goodbye, presence, probe in the crate source found none outside docs.
- Crash or silent loss: no probe. After `NeighbourDown`, the code only updates the neighbour set and emits the event (`gossip/actors/manager.rs:344-362`). I found no path that probes the peer or announces it unreachable. I did not trace whether iroh-gossip reconnects on its own.
- Staleness is a separate, local signal. Endpoint connection outcomes update the address book (`iroh_endpoint/actors/endpoint.rs:336-352` reports the outcome with `report`). A node is stale when its last recorded attempt failed (`addrs.rs:661-690`). Bootstrap nodes are never stale (`addrs.rs:165-166`).
- Stale nodes are skipped during address resolution (`iroh_endpoint/discovery.rs:137`) and by the walker (`discovery/actors/manager.rs:144`). They are not announced to anyone.
- Outgoing failures are not recorded while our own endpoint address is not globally reachable (`iroh_endpoint/actors/endpoint.rs:336-348`). The code's comment says this avoids blaming remote nodes for our local connectivity. Otherwise a failed attempt marks the remote stale.

### Tests covering these paths

## Against the spec (recorded, not judged)

- **D12, gossip carries presence, direct streams carry messages.** p2panda has both primitives. `Endpoint::accept` and `Endpoint::connect` register and open custom ALPNs (`iroh_endpoint/api.rs:130`, `:151`). It has no ack protocol; a direct-stream message layer would be the application's own code.
- **D13, network is a secret; topic and MAC derive from it.** p2panda's network id is public (`lib.rs:301-302`). Its membership handle is the topic, a random 32-byte value the application supplies (`p2panda-core/src/topic.rs:25-29`). No MAC keyed from a secret exists anywhere in the crate. The crate also says the network id is "not secret (yet)" (`lib.rs:207-208`).
- **D14, bootstrap from relay plus cardless stable member.** Relays are opt-in (`iroh_endpoint/builder.rs:31`). A stable endpoint key is possible, since the signing key is caller-supplied (`builder.rs:98`). Bootstrap uses address-book entries, not a ticket.
- **D15, local discovery as an extra.** mDNS is a default feature and a separate builder (`iroh_mdns`). It runs only when spawned. Consistent in shape.
- **D16, no allowlist inside the network.** Default is permissive (`iroh_endpoint/authoriser.rs:101`). The crate root still lists allow and deny lists as future work (`lib.rs:223`, issue #925), though `authoriser.rs` exists. I read the code, not the roadmap.
- **D17, every message proves itself.** p2panda adds no proof to gossip payloads. Only node and transport records are signed (`address_book/actor.rs:194`, `:215`). Estafette would add its own claim and MAC above this layer.
- **D18, introduction replaces heartbeats.** No announce-on-join exists. Discovery walks run continuously, at most 30 s apart by default (`discovery/backoff.rs:47-58`). This is periodic traffic that the spec's reason ("no periodic traffic") excludes.
- **D19, clean stop sends departure.** No departure payload exists. Direct overlay neighbours see `NeighbourDown` after iroh-gossip's disconnect (iroh-gossip `src/net.rs:254-257`). I found no propagation of the disconnect beyond direct neighbours.
- **D20, probe before rumor.** No rumor and no probe exist in the crate. Local staleness comes from connection outcomes (`iroh_endpoint/actors/endpoint.rs:336-352`). The spec's unreachable report has no counterpart.
- **Part 1.7, no mailbox or queue.** The `sync` feature is an append-only log with catch-up of missed messages (`sync/log_sync/api.rs:30`, `lib.rs:167`). It requires a log store (`sync/log_sync/builder.rs:19-21`). Using it would bring store-and-forward into the network.
- **Part 1.9, one owner per network.** The crate has no owner concept. Its default network is a public constant (`lib.rs:316-318`).

## As a whole layer under estafette

What it would impose, from the code:
- **Identity.** One ed25519 key is both the peer id and the transport key (`iroh_endpoint/actors/endpoint.rs:203`). The spec separates a card key from an ephemeral node key bound by a signed claim (Part 1.2, and the round-1 brief's summary of Part 3, which I did not read). p2panda would replace that split.
- **Stores.** The address book is sqlite through `sqlx` 0.9.0 (`p2panda-store/Cargo.toml:68`), in memory by default (`address_book/builder.rs:33-36`). Persisting it means a sqlite file. The `sync` feature adds a log store.
- **Runtime.** Each layer is a `ractor` actor (`ractor` 0.16.2, thread-local spawner). That is a second concurrency model beside tokio.
- **Center.** None by default. No relay is set (`builder.rs:31`), and bootstrap comes from address-book entries. This matches "no center" (Part 1.7) when relays are set by the operator.
- **Versions.** iroh 1.3.0 and iroh-gossip 0.101.0, the same as estafette's round-1 measurements. The added crates are the weight: `sqlx`, `ractor`, and four `p2panda-*` crates.
- **Leak.** The default discovery config shares transport info for all known nodes (see the discovery section). For one topic per network this matters little. For a machine that also knows other topics, it leaks their members' addresses.

What could be taken, one line each:
- **Pattern:** mixing a network id into each ALPN by hash (`lib.rs:321-326`). Domain separation without a MAC.
- **Pattern:** stale marking from connection outcomes, with the local-reachability guard (`endpoint.rs:336-352`).
- **Pattern:** signed node and transport records verified on insert (`address_book/actor.rs:194`, `:215`).
- **Crate:** `p2panda-discovery` PSI exchange, only if estafette wants topic-hash discovery. It was not designed for this spec's one-owner model.
- **Nothing whole:** the gossip, presence, and departure semantics do not match D18-D20 and D16-D17 without replacement.
